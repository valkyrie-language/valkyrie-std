# 图像系统

## 当前定位

图像系统文档只描述图像数据、格式编解码和工具链接线边界，不再复述旧生态项目名、旧门面对象或废弃中间层。

对当前 `valkyrie.v` 路线来说，图像相关能力应当被看作一组独立的数据与编码能力，而不是语言主线的一部分。

## 核心边界

图像系统长期只处理三类问题：

- 像素数据如何表示
- 图像格式如何解码与编码
- 图像产物如何接入资源打包与交付

它不负责：

- 解释语言语义
- 充当统一低层 `IR`
- 反向决定编译主线结构

## 与主线架构的关系

图像处理能力通常出现在 `Encode`、`Package`、资源构建或宿主适配阶段。

典型关系如下：

```text
Source
  -> Semantics
  -> HIR / MIR / Optimize
  -> Partition
  -> Family Lane
  -> Backend Input
  -> Validate / Compile
  -> Encode / Package
      -> 资源编解码
      -> 图像格式转换
      -> 纹理与附属资产组织
  -> ArtifactSet
```

这意味着图像系统是交付链的一部分，不是语言中层本体。

## 统一数据模型

无论最终使用哪种格式，图像系统都需要一个稳定、简单的中性表示来承接像素数据。

最低要求通常包括：

- 宽度
- 高度
- 像素格式
- 像素数据缓冲区
- 色彩空间或相关元数据

这个中性表示只服务于图像编解码与处理，不应被误抬升成通用程序数据模型。

## 格式层职责

每种图像格式都应各自维护自己的：

- 魔数与头信息解析
- 数据结构约束
- 解码规则
- 编码规则
- 基本合法性校验

共享层只保留真正跨格式共用的事实：

- 通用像素表示
- 统一错误模型
- 通用缓冲区读写辅助

## 典型格式

常见格式包括但不限于：

- `PNG`
- `JPEG`
- `BMP`
- `TGA`
- `DDS`
- `EXR`
- `PSD`
- `GIF`

是否支持某种格式，应由资源链和产品需求驱动，而不是为了追求统一大而全的门面。

## 资源链中的使用方式

图像系统在工程里更适合承担这些职责：

- 资源导入时做格式识别
- 构建时做尺寸调整、mipmap 生成或格式转换
- 打包时把图像与其他资源一起组织进 `ArtifactSet`
- 宿主加载时消费已经定型的纹理或图片产物

## 明确禁止

- 禁止让图像系统反向决定语言语义
- 禁止把图像格式层设计成新的统一大对象
- 禁止把宿主平台差异塞进公共像素模型
- 禁止为了某个单一引擎或单一渲染后端污染全部格式抽象

## 一句话原则

图像系统是资源编解码与交付能力，不是编译主线的替代品，也不是新的公共大总线。
