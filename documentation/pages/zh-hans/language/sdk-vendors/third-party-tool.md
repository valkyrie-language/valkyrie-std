# 第三方构建器

## 设计定位

`wechat`、`unity` 这类平台的问题并不只是“把某个 `std` 入口映射到宿主函数”。真正麻烦的部分通常包括：

1. 平台工程目录组织
2. 平台配置文件生成
3. 静态资源收集
4. 胶水代码生成
5. 打包、预览、上传、发布

这些职责不属于 `legion`，而应由平台方自己的第三方构建器负责。

这里的“第三方构建器”是总称，具体形态可以不同：

- 对微信小程序，更像一个独立工具
- 对 Unity，更像一个插件

## 第三方构建器要负责什么

第三方构建器应当至少负责两类事情：

1. 把平台默认 `sdk` 注入当前构建的有效依赖闭包
2. 在 `legion` 输出中间产物之后继续完成平台自己的构建流

因此，第三方平台通常不是只发布一个 `sdk`，而是要同时发布：

1. 第三方 `sdk`
2. 第三方构建器

前者负责能力绑定，后者负责默认注入与后续构建。这也是为什么要把 `sdk` 和构建器分开：能力绑定与平台构建流不是同一类职责，而且不同平台的构建器形态也可能完全不同。

## 与 `legion` 的边界

`legion` 只负责：

1. 通用编译
2. 语义期静态绑定
3. 产出目标平台可消费的中间产物

第三方构建器负责：

1. 平台自己的默认 `sdk` 选择
2. 平台胶水生成
3. 平台工程组织与资源处理
4. 平台打包、预览、上传、发布

它不是 `legion` 插件，只是共享 `nyar` 的基础 build 体系。

## 为什么要隐式注入默认 `sdk`

标准库的 `clr` / `jvm` adaptor 一般也不要求用户每次显式写出依赖。第三方平台应有相同体验：

- 默认情况下，构建器按平台注入一组默认 `sdk`
- 用户不需要为日常构建反复手写同样的 `sdk` 依赖
- 只有锁版本、测试版本或覆盖默认实现时，才显式写出依赖

这也是为什么 planner 应看“有效依赖闭包”，而不是只看 manifest 里的显式依赖。

## 微信小程序工具

微信小程序侧需要的是一个独立工具，推荐流程是：

1. 读取项目 manifest 与 target / publish 信息
2. 隐式注入 `tencent.wechat.sdk`
3. 调用 `legion` 产出微信小游戏可消费的中间产物
4. 自动生成微信侧胶水与工程配置
5. 继续执行小游戏工程组织、预览、上传、发布

应用项目可以非常轻：

```von
{
    name: "demo.wechat.game",
    dependencies: {
        "std": "workspace"
    },
    build: [
        {
            target: "wasm32-unknown-browser-wasm",
            publish: ["mini-game"]
        }
    ]
}
```

这里不显式写 `tencent.wechat.sdk`，因为默认由腾讯自己的微信小程序工具注入。

## Unity 插件

Unity 侧更适合表现为插件型接管，推荐流程也类似，只是后半段不同：

1. 读取项目 manifest 与 target / publish 信息
2. 隐式注入 `unity.engine.sdk`
3. 调用 `legion` 产出 `MSIL` 或其他 Unity 可消费的中间产物
4. 自动把产物写入 Unity 工程目录
5. 触发 Unity Editor 或批处理继续完成最终构建

它可以表现为 Unity 编辑器插件、导出插件或自动化集成脚本，但职责上仍属于第三方构建器层，而不是语言内建机制。

## 构建器不应该做什么

第三方构建器不应：

1. 修改 `std` 语义
2. 绕过 planner 直接硬改 `host_provider`
3. 在运行时决定绑定关系
4. 要求用户在业务源码里手写平台胶水

特别是像微信小游戏这类平台，JS 胶水应由构建器生成，而不是在源语言里伪造一堆手写桥接函数。

## 显式依赖何时仍然有意义

即使默认支持隐式注入，显式依赖仍然保留价值：

1. 锁定某个第三方 `sdk` 版本
2. 在 CI 中验证候选版本
3. 覆盖构建器内置默认版本
4. 复现某个历史构建问题

例如：

```von
dependencies: {
    "std": "workspace",
    "tencent.wechat.sdk": "1.2.3"
}
```

## 与 `bind` 的关系

第三方构建器负责把默认 `sdk` 放进候选集，但不负责替 planner 猜冲突结果。

如果当前有效依赖闭包同时看见：

- `tencent.wechat.sdk`
- `std.adaptor.wasm`

并且两者都提供 `std.net.get` 的宿主实现，那就说明当前有效依赖闭包还没有收窄到唯一实现。

也就是说：

- 构建器负责“把谁带进来”
- planner 负责“看见哪些实现”
- `bind` 负责“选中实现之后如何接到最终宿主符号上”

## 一句话总结

第三方平台如果只提供 `sdk`，能力绑定能成立，但真实构建流仍然缺一半；因此完整生态必须同时提供：

- 第三方 `sdk`
- 第三方构建器

其中：

- 微信小程序侧的构建器通常是独立工具
- Unity 侧的构建器通常是插件
