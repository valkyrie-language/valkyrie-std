# 应用怎么切：横切、纵切与 DAP

## 背景：规模上来之后怎么切

应用变大时，总会面对同一问题：代码按什么边界收口，才能改得动、测得清、协作不踩脚。两条常见几何方向一直并存：

| 几何 | 做法 |
|------|------|
| **横切** | 按技术层铺开：表现 / 应用服务 / 领域 / 基础设施，业务能力横跨多层 |
| **纵切** | 按业务能力竖切：每个切片自带编排、适配器与测试，层在切片内部再现 |

横切和纵切**都合法**。没有「只有纵切才算架构正确」的天条。

## 低耦合、高内聚始终是尺子

无论横切还是纵切，评判尺度仍是：

- **高内聚**：改一块业务时，相关代码尽量落在少数边界内；
- **低耦合**：边界之间靠明确端口协作，而不是互相钻实现。

过碎的「纯净分层」或过胖的「上帝模块」都会同时伤害二者。切法是手段；低耦合、高内聚才是指导思想。

## 为何叫 Domain，而不是 System

在 DAP 里，业务能力边界叫做 **Domain**，而不是口语里的「System」。

「System」歧义太多：操作系统、运维系统、口语里的「整个系统」……阅读与检索时容易串台。用 Domain 标出业务边界，用 Adapter 标出可替换接缝，用 Host 收口组合根，语义更稳。

## 默认叙事与弹性

Atlas / Asgard 文档与示例里，**纵切 Domain** 是常见默认：一块业务能力一个目录，Adapter（HTTP、存储、平台 UI）挂在旁边。这不否定局部横切——共享内核库、统一中间件管道、跨 Domain 的技术层工具，都可以存在。

强制「只能纵切」或「只能按层横切」都会变成教条。阶段不同、团队不同，可以偏一种几何，只要仍守住低耦合、高内聚，并在评审里说清取舍。

## DAP 的三角

在上述脉络下，**DAP（Domain Adapter Pattern）** 只做三件事：

1. 用 **Domain** 命名业务边界，减少 System 歧义；
2. 用 **Adapter** 标出可替换接缝；
3. 用 **Host** 收口组合根，避免业务堆进组合根。App（`XxxApplication`）按目标平台自动派生、很少自定义；用户默认写 **`XxxHost`**，并在其上挂 Domain / Adapter。

它是组织代码的**指导思想与推荐形状**，不是部署拓扑规定，也不是禁止横切共享。机制细节见 [DAP 机制](dap.md)。
