# migrations 回放

## 什么是 migrations 回放

维护有序 migration 文件链 + 库内版本表（如 `schema_migrations`），启动或发布时按版本号**依次执行尚未应用的脚本**（EF Migrations / Flyway / `sqlx migrate` 等常见模型）。

---

## 它本想解决什么

在 ORM / 交付工具普及之前，改库往往靠口头约定或随手 SQL，结果是：

- 开发库、测试库、生产库形状对不齐；
- 「这列是谁加的、该不该有默认值」说不清；
- 发布时靠人记得跑哪些脚本，易漏、易乱序。

**migrations 回放**因此被提出，承诺大致是：

1. **把结构变更写成可版本化的脚本**，和代码一起进仓库；
2. **用版本表记录「已经应用到哪一步」**，工具自动补跑差额；
3. **同一套文件链**服务所有环境，保证「按顺序走完就一致」。

在**短周期、单人、环境少、库几乎总是从空库或同一快照长起来**的项目里，这套叙事很有吸引力，也确实能减少「忘跑脚本」一类低级错误。问题不在「提出时毫无道理」，而在于它把**过程日志**当成了**结构真源**，并在协作尺度放大后必然露出裂缝。

---

## 长寿命、多人协作里怎样失效

在「历史悠久、多人、多分支、多环境」项目里，失效是常态，而不是边角案例。

### 版本号绿了，形状却不对

回放成功只证明：**版本表认为**这些脚本跑过了。它不证明当前库等于「今天应用心里的目标 schema」。

常见现实：

- 有人在生产上热修过一列、加过索引、改过类型；
- 从备份还原后版本表与真实对象不一致；
- 某环境跳过了中间脚本，或手工标记了「已应用」。

此时工具仍可能报告 up-to-date，而查询/绑定已经按**另一套形状**在检查。双真源（文件链 + 真实库）一旦漂移，版本表变成安慰剂。

### 历史不可变，却又不得不改

规则是：已在生产回放过的 migration **不能改**（改了无法让旧环境重放同一语义）。  
但长项目里总会发现：当年脚本有 bug、在某种方言上不安全、或依赖了后来删除的对象。

于是出现补偿 migration、空 migration、「把错误修在下一步」的长尾。仓库里的迁移史变成考古层，新人不敢碰，老人靠口头传说解释「为什么 V047 是空的」。协作成本随时间**单调上升**。

### 分支与合并把「顺序」撕碎

migrations 模型隐含一条**全局全序**：脚本有编号，必须按序应用。多功能分支并行开发时：

- 两个分支各写一个「下一个版本号」→ 合并冲突；
- 依赖顺序在分支 A/B 上不同 → 合入后某环境回放失败；
- 试图 rebase / 重编号迁移史 → 已发布环境的版本表对不上，事故面更大。

代码可以用 rebase 整理；**已回放的迁移史不能诚实 rebase**。这与现代多分支协作直接冲突。

### 「全员同轨」假设经常不成立

回放假定：每个环境都从同一祖先、按同一顺序前进。现实里常见：

- 只升级部分租户 / 分片；
- 预发库落后大版本，生产已热修；
- 本地库来自别人 dump，版本表是别人的。

假设一破，工具的「自动补跑」要么拒绝工作，要么在错误前提上继续，留下更难查的中间态。

### 过程冒充状态：检查与升级说的不是同一种话

应用真正需要的是：**目标状态**（最新 schema）与 **当前状态**（这台库现在的形状）。  
migrations 链保存的是：**怎样一步步走过来的过程日志**。

用日记本当图纸的后果是：

- 静态检查若跟着「某个历史版本」走，类型世界会分叉；
- 静态检查若只认最新 schema，又与「库还停在 V030」的现实打架——而回放工具仍坚持「按差量脚本补」，不直接回答「当前 vs 目标差在哪」。

短 demo 里两边碰巧重合，看不出裂痕；项目一长，裂痕变成主旋律。

### 最终仍在手写「真正的升级」

当链不可信时，团队往往退回：

- 删库重建（只对非生产友好）；
- 或手写一份「从现状修到目标」的巨型 SQL——也就是**一次性、针对当前库的升级计划**。

这说明：真正管用的操作，本来就是 [UpgradePlan](upgrade-plan.md) 在正规做的事；migrations 回放并未消灭这个问题，只是推迟并加价。

---

## 它为什么是反模式

**以 migrations 文件链 + 版本表回放作为结构协作真源**，在 Atlas 的目标场景（多人、多环境、长寿命、以 Hermes 最新 schema 为 SoT）下是**反模式**：

| 它承诺的 | 实践交付的 |
|----------|------------|
| 环境最终一致 | 版本号一致 ≠ 形状一致 |
| 变更可追溯 | 可追溯的是过程，不是当前该有的状态 |
| 自动化省心 | 省的是短项目的心；长项目用补偿脚本与合并冲突还债 |
| 一份脚本服务所有库 | 真实库路径分叉后，同一条链无法诚实服务所有人 |

Atlas 因此约定：

- **状态真源**：仓库内**最新** Hermes schema；绑定与 [schema 静态 query 检查](schema-static-query-check.md) 对齐它。
- **环境对齐**：当前 schema vs 目标 schema → [UpgradePlan](upgrade-plan.md)（可物化 SQL、可有限编辑）→ **一次性 Apply**。
- **不把** migrations 版本表回放做成一等公民工作流；工具链也不以「维护 / 回放 migration 链」为默认叙事。

短周期单人项目里 migrations 曾经好用，并不否定上述判断：一旦协作与时间尺度达到 Atlas 要服务的范围，它解决的问题会被它制造的问题淹没。Atlas 因此改用状态差驱动的 [UpgradePlan](upgrade-plan.md)，而不再把 migrations 回放当作结构协作真源。
