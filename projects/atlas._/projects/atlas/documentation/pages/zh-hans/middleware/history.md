# 从历史到中间件

## 背景：业务里长满了「进出门手续」

HTTP 服务稳定之后，真正难缠的往往不是某一个 Handler 的业务公式，而是**每一单请求都要办的手续**：

- 进来时：解析身份、鉴权、限流、校验 Content-Type、打开追踪 span；
- 出去时：统一包装错误、写访问日志、刷 CORS 头、结束 span；
- 异常时：别让栈轨迹直接喷给客户端，也别让连接半开着悬挂。

若每个 Handler 自己写一遍，后果很具体：漏鉴权、日志格式不统一、改一处策略要碰几十个文件。人们需要把这些手续从业务方法里抽出去——抽到「请求进业务之前 / 出业务之后」的公共层。这一层后来有很多名字：过滤器、拦截器、管道、中间件。

## 早期形态：过滤器与拦截器

### Servlet Filter / 前端控制器前后

Java Servlet 时代的 **Filter** 链是早期标准化做法：容器按配置顺序调用 `doFilter`，Filter 里再 `chain.doFilter` 把控制权交给下一环或 Servlet。思想已经是「包在业务外面」，但 API 偏容器生命周期，链式调用靠约定，组合方式因规范与应用服务器而异。

### 拦截器（Interceptor）

MVC 框架里的 HandlerInterceptor、各种 RPC 拦截器，把切点放在「进 Action 前 / 后」。相对 Filter，更贴近框架路由与 Handler 模型；相对后来的中间件，仍常是**单向 before/after 列表**，而不是强调「同一函数里 before → next → after」的闭环叙事。

### 管道与委托

另一些栈用 **pipeline**：显式的步骤列表，每步处理上下文再交给下一步（或返回）。管道强调可组合与顺序；不同实现在「返回时是否自动经过外层」上不一致——有的要自己记得在返回路径写收尾逻辑。

这些形态共同解决了「别把手续写进每个业务方法」，也留下一个问题：**进出成对的逻辑**（计时开始/结束、事务开/提交、日志进/出）如何自然地写在同一处，又保证无论成功、失败、短路都能跑到外层收尾。

## 为何需要更清楚的「里外」模型

列表式 before/after 容易出现：

- before 开了资源，业务抛错后 after 漏执行；
- 短路（鉴权失败）时，外层日志不知道该记成功还是失败；
- 多个横切嵌套时，人脑难以对齐「谁包着谁」。

理想写法接近：

```text
手续甲：进入
  手续乙：进入
    业务
  手续乙：离开（无论业务成败，只要乙曾进入）
手续甲：离开
```

这正是一层层包起来的结构——后来被广泛称作**洋葱模型**（onion model）：外层中间件包着内层，请求向内穿，响应（或错误）再向外穿。

## 中间件一词的流行

在 Node（Connect / Express / Koa）、以及受其影响的众多 HTTP 框架里，**middleware** 成为默认词：一个函数拿到上下文与 `next`，先做进入逻辑，`await next()`（或回调 `next`）进入内层，回来后再做离开逻辑。Koa 等实现把「同一段代码里的前后」与异步栈结合，使洋葱叙事与工程实践对齐。

其它生态有等价物：ASP.NET 的 middleware pipeline、反向代理与 API 网关上的 filter chain——细节不同，**请求向内、响应向外、外层最后收尾**的几何结构相同。

中间件相对「裸 Filter 列表」的要点通常是：

1. **显式 `next`**：内层（含最终业务）由当前中间件决定何时调用；
2. **对称的进出**：`next` 前后的代码自然对应 before/after；
3. **可短路**：不调用 `next`（或设置短路标志）则业务不再执行，但已进入的外层仍可在返回路径收尾（具体取决于实现是否用 try/finally 或等价结构）。

## 通向洋葱模型

把多层 middleware 叠在一起，几何上就是洋葱：

```text
        ┌─────────────────────────────────┐
        │  middleware A（外）               │
        │   ┌───────────────────────────┐ │
        │   │ middleware B                │ │
        │   │  ┌─────────────────────┐  │ │
        │   │  │ 业务 Handler         │  │ │
        │   │  └─────────────────────┘  │ │
        │   └───────────────────────────┘ │
        └─────────────────────────────────┘
请求 ─────────────────────────► 中心
响应 ◄───────────────────────── 中心
```

历史脉络可以收成一句：从「每个业务自己办手续」，到 Filter/拦截器「在外面办手续」，再到 middleware「用 next 把进出写在同一层」，最终用洋葱模型描述多层嵌套时的请求/响应穿行方向。

洋葱模型本身的执行规则、短路与 Atlas 中的对应实现，见 [洋葱模型](onion-model.md)。
