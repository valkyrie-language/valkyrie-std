# 从 IoC/DI 到 Wire

## 背景：对象图失控之后

后端服务稍具规模，就会长出一层层协作对象：处理请求的 Handler、领域 Service、访问库的 Repository、缓存、队列、外部 HTTP 客户端……若每一层都在方法里 `new` 下一层：

- 换实现（测试替身、另一家缓存、只读副本）必须改业务源码；
- 生命周期（进程单例还是每请求一个）散落在各处 `new` 里，难以统一；
- 依赖关系只能靠读代码猜，新人难建立「系统怎么拼起来」的图景；
- 同一依赖被多处创建，连接数、配置、关闭顺序都容易出错。

人们需要的不是消灭对象，而是把「**谁创建、谁持有、谁在何时注入**」从业务主路径里抽出去——这就是后来常说的控制反转与依赖注入要回答的问题。

## 什么是 IoC

**IoC（Inversion of Control，控制反转）**：对象「什么时候被创建、依赖谁、生命周期由谁管」不再由业务代码全程一手包办，而交给框架或宿主来调度。

```text
没有反转：
  Handler 自己 new Service
  Service 自己 new Repository
  Repository 自己 new DbConnection
  → 业务代码控制整棵对象图的建造与销毁

有反转：
  宿主 / 框架先准备好协作对象
  再把它们交给 Handler / Service 使用
  → 业务代码声明「我需要什么」，不负责「怎么拼出来」
```

IoC 是更宽的范畴：事件驱动、模板方法、插件回调、依赖注入，都可以是某种控制反转。后端 Web 里日常说的 IoC，多半落在**对象图如何组装**。

## 什么是 DI

**DI（Dependency Injection，依赖注入）** 是实现 IoC 的一种主流手段：协作对象从**外部传入**使用方，而不是使用方在内部构造它们。

| 方式 | 做法 | 特点 |
|------|------|------|
| 构造注入 | 创建时传入全部依赖 | 依赖集一目了然；对象可做成不可变 |
| 属性 / 字段注入 | 创建后再写入依赖字段 | 灵活；易出现「半初始化」对象 |
| 方法注入 | 调用某方法时传入 | 适合偶发依赖 |

「注入」强调方向：依赖朝使用方流动。DI **不等于** 必须有容器——手写构造函数传入 `OrderStore`，已经是 DI。

不是所有 `new` 都该反转。纯值、局部临时对象、算法内部结构，继续本地创建即可。IoC/DI 针对的是**跨边界协作端口**：换实现、换环境、做测试替身时，不应改业务主流程里的构造逻辑。

## 传统解法：在反射容器之前

在「启动扫程序集、按特性自动接线」成为主流之前，团队已经用过多种办法缓解对象图问题。它们至今仍合理，也构成理解后来反射容器的前提。

### 手写组装（Poor man's DI）

在 `main`、组成根（composition root）或测试入口里，显式 `new` 出整棵图，再传入顶层对象：

```text
store   = new PgOrderStore(conn)
system  = new OrderSystem(store)
host    = new Host(system)
```

依赖方向正确，图在一处可读。代价是框架尺度下样板多、易漏接，每个测试/环境要复制或分支一段组装代码。

### 工厂与抽象工厂

把「如何创建」收进工厂方法，业务只依赖抽象。能隔离实现，但工厂本身仍要被创建与传递；工厂多了又变成另一棵要管理的图。

### 服务定位器（Service Locator）

业务向全局或上下文「按名/按类型要实例」。调用点少改构造签名，但依赖从类型签名上消失，变成运行时查找；测试与审阅更难，常被视为 DI 的反面教材（依赖仍在，却藏起来了）。

### 模块 / 手动注册表

用模块初始化函数或显式注册表绑定接口到实现，启动时装载。比纯全局定位器清晰，仍多靠约定与字符串键，编译器帮助有限。

这些传统解法共同说明：**问题早就在，手段是「显式组装」或「运行时查找」**。下一步大规模工程想要的是：少写组成根样板，又尽量自动满足构造函数——反射式 IoC 容器因此上台。

## 反射式 IoC 容器

以 Spring、早期大量依赖反射的 .NET 容器等为代表，典型承诺是：

- **注册**：类型或接口绑定到具体实现（也可约定扫描）；
- **解析**：按类型 / 名称取出实例；
- **生命周期**：单例、作用域（如每请求）、瞬时；
- **图组装**：反射读取构造函数与特性，递归 new 并注入，直到对象图完整。

相对手写组成根，反射容器显著减少样板，使「加一个 Service 就能被扫进去」成为可能。不少生态还在同一容器上叠 **AOP 代理**（拿到的 Bean 已被日志/事务切面包装），于是「注入」与「切面」常被当成一件事。Atlas 把二者拆开：对象端口用 **Wire**；请求横切用 **中间件**（见 [AOP 与中间件](../middleware/aop.md)）。

## 反射式容器的痛点

规模与寿命拉长之后，同一套「运行时才看清的接线」反复露出成本。

### 接线在编译器视野之外

依赖是否满足、绑的是哪个实现，常常要等进程启动或第一次解析失败才知道。重构改名、删除实现时，运行时类型名与配置键成为第二套易碎契约；IDE 难以给出与普通字段同等严格的保证。

### 隐式图难以审阅

递归满足构造参数少写了代码，也把「谁依赖谁」藏进框架魔法。循环依赖、错误作用域（请求级对象被当成单例）的诊断路径长，读 Handler 源码看不到完整对象图。

### 启动与运行成本

扫描、建图、代理、延迟工厂增加启动时间与运行开销。面向 AOT、弱化反射元数据的交付形态时，动态创建与扫描本身就不友好。

### 测试替换仍要懂容器咒语

理论上可换 mock，实践中往往要复制注册仪式或依赖框架专用测试宿主。「类型上声明了依赖」与「测试里如何换掉」中间隔着容器 DSL，而不是同一种静态可见的声明。

### 边界被模糊

容器一旦成为默认文化，不该进图的对象也被注册，图更大、更慢、更难懂。IoC 本该守住协作端口边界，全自动扫描却容易把边界冲掉。

## 解决思路

目标不变：业务声明需要什么，宿主提供什么，测试能换实现且少改业务代码。改变的是**接线如何被看见、何时失败**。

1. **声明留在类型上** — 依赖是源码里的明确标记，而不是仅存在于外部扫描结果。
2. **接线代码可生成、可进编译** — 根据声明生成显式赋值；尽量在编译期/生成期失败，而不是第一次请求才炸。
3. **容器退回「实例袋子」** — 宿主边界负责注册与取出；不反射扫全世界、不隐式猜构造函数。图的形状以生成代码为准。
4. **替换发生在注册点** — 生产与 mock / sink / null 只换容器里的实例，见 [非真实 Wire](doubles.md)。

手写组成根满足「可见」，框架尺度易漏；反射容器满足「少写」，牺牲可见与 AOT。下一条路是：**声明 + 代码生成 + 薄容器**——既保留 DI 方向，又把接线拉回编译期可审阅的世界。

## Wire

Atlas 把上述思路收成 **Wire**：

- 用 `wire` 字段在类型上声明协作端口；
- 用 `WireInjector` 生成 `AtlasWireable.apply_wire`，从容器拉取实例并赋值；
- 用 `AtlasWireContainer` 在 `AtlasHost` / 请求边界持有并提供实例（含测试替身）。

相对反射式容器：Wire **不**在运行时扫描字段表；依赖集以源码声明与生成代码为准。相对纯手写组成根：System / Controller 有统一注入协议，换实现不必改业务方法体。Wire **不**承担 AOP：请求周围的鉴权、日志、统一异常等横切走中间件管道。

机制细节见 [Wire 机制](wire.md)；与代数效应的分工见 [Wire 与代数效应](effects.md)；横切与 AOP 见 [Middleware · AOP](../middleware/aop.md)。
